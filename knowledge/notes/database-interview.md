# 一、关系型数据库基础

关系型数据库用表、行、列和约束表达结构化数据，靠主键、唯一约束、外键和检查约束保证数据规则。面试中不要只说“数据库存数据”，要能说明：谁拥有数据、读写路径是什么、并发时如何保证正确性、索引如何支撑查询。

常见对象：

- 主键：唯一标识一行；尽量稳定、短、不可变。
- 唯一索引/约束：防止业务重复，例如手机号+账期唯一。
- 外键：表达引用完整性；高写入或跨服务场景也可能用应用层约束，但要说明一致性代价。
- `NOT NULL`、`CHECK`：把能由数据库保证的规则下沉到数据库。
- 事务：把多条读写组成一个原子工作单元。

# 二、索引与查询优化

## 1. B+Tree 索引的面试说法

B+Tree 通过多层有序节点缩小搜索范围，叶子节点按顺序连接，适合等值、范围和排序查询。索引不是越多越好：会增加写放大、磁盘和维护成本。

联合索引遵循最左匹配原则的常见版本：`(a, b, c)` 可高效支持 `a`、`a,b`、`a,b,c` 的前缀条件；跳过 `a` 通常无法完整利用索引。范围条件、函数包裹、隐式类型转换、前导 `%` 可能让索引效果下降。

## 2. 设计和验证索引

1. 从真实查询出发：过滤、连接、排序、返回列和选择性。
2. 让高选择性和稳定的等值列靠前，再考虑范围和排序；具体顺序必须通过执行计划验证。
3. 使用 `EXPLAIN`/`EXPLAIN ANALYZE` 看访问类型、候选索引、实际行数、回表、排序和临时表。
4. 避免 `SELECT *`、深 offset 分页、对索引列做函数、无条件模糊查询。
5. 覆盖索引可减少回表，但索引过宽会降低写入性能。

## 3. 分页

`LIMIT offset, size` 越到后面越需要扫描和丢弃前面的行；并发插入/删除还可能重复或漏数据。游标分页用稳定排序键，例如：

```sql
SELECT id, created_at, title
FROM articles
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

排序键必须唯一或由唯一字段补足，否则翻页边界不稳定。

# 三、事务与 ACID

- **Atomicity 原子性**：事务内全部成功或全部回滚。
- **Consistency 一致性**：事务前后满足约束和业务不变量。
- **Isolation 隔离性**：并发事务互不产生不允许的中间影响。
- **Durability 持久性**：提交成功后，即使进程重启也应可恢复。

事务边界应覆盖一个业务不变量，而不是随便把很多 SQL 包起来。事务越大，持锁和冲突越久；外部 HTTP 调用通常不应长时间放在数据库事务内。

## 1. 隔离级别和异常

| 隔离级别 | 可能现象 | 典型取舍 |
| --- | --- | --- |
| Read Uncommitted | 脏读、不可重复读、幻读 | 很少使用；具体数据库可能提升实现级别 |
| Read Committed | 避免脏读；同一事务两次读可能不同 | PostgreSQL 默认，常见业务默认 |
| Repeatable Read | 同一事务快照更稳定；仍需关注写冲突/幻读实现差异 | 报表或一致读场景 |
| Serializable | 结果等价串行执行，冲突时可能回滚重试 | 强一致但吞吐和重试成本更高 |

“幻读”是同一条件两次查询，第二次多出或少了符合条件的行；“不可重复读”是同一行两次读取值不同；“脏读”读到了未提交数据。

PostgreSQL 使用 MVCC，让语句看到某个数据快照；读通常不阻塞写，但仍可使用行锁或显式锁处理特定冲突。不同数据库对 Repeatable Read、间隙锁和 MVCC 细节不同，面试时要先说数据库类型。

## 2. 锁与并发更新

- 悲观锁：`SELECT ... FOR UPDATE` 先锁住要修改的行；适合库存、余额等冲突成本高的场景。
- 乐观锁：增加 `version` 或更新时间条件，更新影响行数为 0 时判定冲突并重试/提示。
- 唯一约束是并发去重的最后防线；应用层“先查再插”不是原子操作。
- 死锁来自循环等待，例如事务 A 持有行 1 等行 2，事务 B 持有行 2 等行 1。统一访问顺序、缩短事务、合理索引和捕获死锁重试可以降低风险。

## 3. 事务代码结构

```text
BEGIN
  校验并读取必要数据
  锁定或检查版本
  写入主表和从表
  写入 outbox / 审计记录
COMMIT
失败 → ROLLBACK，并根据错误类型决定是否重试
```

跨数据库或跨服务不要假装一个本地事务可以覆盖全部系统；可用 Outbox、消息重试、幂等消费和补偿动作实现最终一致性。

# 四、缓存与 Redis

## 1. 为什么缓存

缓存用空间和一致性复杂度换取更低延迟、更高读吞吐和更少数据库压力。缓存值是持久数据的副本，必须能被重建；不能把唯一真相只放在易失缓存里。

## 2. 常用模式

- **Cache Aside**：读缓存，未命中读数据库并回填；写数据库成功后删除或更新缓存。通用且容易理解。
- **Read Through**：缓存层负责未命中加载；业务代码更简单，但依赖缓存组件能力。
- **Write Through**：写缓存同步写后端；一致性较强，写延迟更高。
- **Write Behind**：先写缓存，异步落库；吞吐高但数据丢失和顺序风险更大。

## 3. 缓存三大问题

- **穿透**：大量请求不存在的 key。用参数校验、布隆过滤器、短 TTL 空值缓存。
- **击穿**：一个热点 key 过期瞬间大量回源。用互斥锁、singleflight、逻辑过期或热点不过期。
- **雪崩**：大量 key 同时过期或缓存集群故障。用 TTL 加随机抖动、分批预热、限流、降级和多级缓存。

更新策略要明确：先更新数据库再删缓存通常更容易保证最终一致；删除失败要有重试、消息或定时修复。并发读可能在删除后把旧值回填，因此高一致场景要用版本号、延迟双删、写入队列或直接绕过缓存，不能把“延迟双删”当万能方案。

## 4. Redis 面试要点

- String 适合计数、简单对象；Hash 适合字段集合；List 适合队列/列表；Set 适合去重；Sorted Set 适合排行榜和时间分数；Stream 适合带消费组的消息流。
- `MULTI/EXEC` 将命令顺序执行，执行期间其他客户端命令不会插入；它不是跨 key、跨实例的关系型数据库事务，也不自动回滚已经执行的命令。
- Lua 或 Redis Function 可把“检查 + 修改”放在服务端一次执行；仍要考虑脚本耗时和集群 key 槽位。
- 设置 `maxmemory` 和淘汰策略；LRU/LFU、volatile/allkeys 的选择取决于是否只有带 TTL 的 key 可以淘汰。
- 分布式锁要设置 TTL、唯一 token 和安全释放；业务关键写入还需数据库约束/事务兜底，不能只依赖锁。

# 五、数据一致性与高并发

## 1. 单体和单库

优先用数据库事务、唯一约束和行锁保证强一致。缓存、搜索索引、向量库等是派生数据，使用事件或 Outbox 异步更新，并允许重放和补偿。

## 2. 多服务

跨服务写入采用“本地事务 + Outbox”：主事务同时写业务记录和待发送事件；后台投递事件，消费者幂等处理并记录状态。消费失败重试，超过次数进入死信或人工处理。

## 3. 读写热点

热点读：缓存、只读副本、预计算和分页。热点写：分片计数、队列削峰、批量写、避免单行成为全局锁。先测量 QPS、P95、锁等待和数据库 CPU，再决定优化，不要只凭感觉拆库分表。

# 七、面试高频问法

**问：为什么有索引还慢？**

答：先看执行计划；可能是选择性低、联合索引顺序不匹配、范围后无法继续利用、隐式类型转换、函数/前导模糊匹配、回表过多、排序或锁等待。索引只解决访问路径，不解决糟糕的查询和下游瓶颈。

**问：缓存和数据库如何保证一致？**

答：先定义允许的陈旧窗口。常见 Cache Aside 是写库成功后删缓存，删除失败用重试/消息补偿；对强一致数据可读库或使用版本校验。不要只说“更新缓存”，要说明并发回填和故障处理。

**问：事务隔离级别怎么选？**

答：先明确并发异常和业务不变量，再选择最低满足要求的级别；余额/库存可能需要锁或串行化，普通查询通常 Read Committed 足够。高隔离带来的冲突必须有重试策略。
